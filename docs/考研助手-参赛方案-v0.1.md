## 0. 先说三个结论

**结论一：OCR 这一环可以砍掉，改成「版面感知抽取 + LLM 还原 LaTeX」。**

工作区里的 40 份 PDF 全部是 LaTeX 排版的矢量文档，不是扫描件：154 页里光栅图片数量为 **0**，公式是字体绘制出来的矢量字形。对这类文件做整页 OCR 是负优化——OCR 会把分式识别成线性文本，把矩阵识别成乱码，反而丢掉你本来就有的结构。真正要做的是按坐标抽取文字片段，再让模型把这些片段重组成 LaTeX。工期从「一周多」压到「两天」。

**结论二：试卷里没有答案，答案必须外部引入。**

我逐份检查了 40 份卷子，「答案 / 解析 / 参考答案」的出现次数都是 0，只有答题注意事项。你的判卷、reviewer 复核、错题本三条链路全部依赖答案，这一环不能等到后面补。好消息是：这批 PDF 出自公开仓库 [CHNragdoll/anki-pipeline](https://github.com/CHNragdoll/anki-pipeline)，它的 Release 同时提供**答案速查**和**答案详解**两种 PDF。我实测下载了数学二答案速查（92 页），1987 年那页可以直接读出：选择题 D/C/B/D、填空题五道、解答题标注「见解答末尾结论」。**答案源已解决，但要自己对齐到题目粒度。**

还有一个容易漏掉的前提：**官方只公布参考解答，从不公布评分细则。** 所以解答题的 rubric 必须自己从参考解答反推（见 §6.1）。这是「判卷」能否成立的关键，不是可选项。

**结论三：关系型数据库 + 树/闭包表，不要图数据库；向量只做三件小事。**

你的直觉是对的（「不能用向量存储」），但分层需要调整一下。P0 范围内 501 道题、137 个知识点节点，图数据库买不到任何东西，反而多一套运维和一个在 Qoder Sites 上跑不起来的组件。知识点是**树 + 少量跨边**，用 `parent_id` 加一张闭包表就够，深度只有 3–4 层。向量真正的价值在三个小地方，见 §3.6。

闭环的关键不是「能出题」，而是**同一条链路上的四份数据能互相喂养**：判卷产生的错因 → 错题本的掌握度 → 复习计划的时间点 → 下次组卷的选题权重。这条数据流跑通，产品才成立。

## 3. 数据层设计

### 3.1 为什么不是图数据库

知识点结构是：一棵 3–4 层的树（高数 5 章 / 线代 6 章 → 节 → 考点），加三类稀疏跨边：

- `prereq`：A 是 B 的前置（诊断排序要用）
- `confusion`：A 与 B 易混（错因归因要用）
- `same_method`：A 与 B 解题方法同源（变式生成要用）

规模：137 个节点（2 门 + 11 章 + 124 考点），跨边最多几百条。这个量级下，Neo4j 的收益是「查询写起来顺一点」，代价是：多一个数据库进程、多一套部署、Qoder Sites 的后端只提供托管关系库和函数，跑不起它。**结论：PostgreSQL + `parent_id` + 闭包表。**

闭包表的实际收益很具体：用户选「一元函数微分学」，你要拿到它下面所有考点的题目，一次 JOIN 解决，不用递归。

```sql
-- 组卷：选一个章节，取它所有子孙考点的题
SELECT q.* FROM questions q
JOIN question_knowledge qk ON qk.question_id = q.id
JOIN knowledge_closure c ON c.descendant = qk.node_id
WHERE c.ancestor = :chapter_id
  AND q.qtype = ANY(:types)
  AND q.status = 'published'
  AND q.id NOT IN (SELECT question_id FROM attempts WHERE device_id = :dev AND correct);
```

137 个节点 × 平均深度 3 → 闭包表不到 450 行，写一次全量重建，维护成本几乎为零。

> 什么时候该换图数据库？当你要做「多跳路径推荐」并且查询变成在线实时的时候。你的场景是「一次性算好推荐顺序」，SQL 足够。别为了简历好看上 Neo4j。

### 3.2 为什么不能把题库做成向量库

向量检索的本质是「按语义相似度返回 Top-K」，它回答不了组卷真正要问的问题：

- 「这题**严格属于**极限的四则运算，不是洛必达」→ 需要精确标签
- 「2020 年以后的题，难度中档，我没做过」→ 需要结构化过滤
- 「这 6 道题不能重复考查同一个点」→ 需要约束满足

向量检索会给你「看起来像」的题，而你需要的是「确定是」的题。

> **一处更正**：我早先写「数学题干高度同质，向量相似度天然接近」，这个说法**没有实测支撑，已撤回**。实测 2024–2026 三年 53 道题的题干，3-gram Jaccard 相似度中位数 0.009、最高 0.193、相似度 > 0.3 的配对占比 **0%**——题干在字面上差异极大。（唯一一对接近 1.0 的是「考生须知」模板页，属于解析时要剔除的噪声。）语义嵌入层面的相似度我没有实测，所以不拿它当论据。
>
> 结论不变，但理由要换成站得住的：**向量做不了精确过滤**。它回答不了「排除我做过的」「只要 2020 年后的」「难度必须是中档」这类约束，而这些恰恰是组卷的硬需求。

**所以：题库的存储与检索是结构化的，向量只做辅助，见 §3.6。**

### 3.3 表结构草案

```sql
-- 试卷
papers(id, year, subject, paper_variant, source_url, page_from, page_to, note)

-- 题目（真题与 AI 原创同表，用 source 区分）
questions(
  id, paper_id, seq_label,        -- seq_label 存原始编号如 '九(1)' / '1'
  section,                        -- choice / blank / solution
  qtype,                          -- single_choice / fill_blank / free_response
  stem_latex,                     -- 题干（LaTeX，前端 KaTeX 渲染）
  sub_items_json,                 -- 该题下的小问 (1)(2)，不拆行
  options_json,                   -- 选择题选项
  answer_latex, answer_source,    -- 'official' / 'ai_verified'
  solution_latex,                 -- 解析（可空，按需加载）
  score,                          -- 该题在原卷中的分值，照实存，不重分配
  difficulty,                     -- 'easy' / 'medium' / 'hard' 三档
  difficulty_obs,                 -- 实测得分率（样本足够后用于校正，可空）
  difficulty_source,              -- 标注依据（锚点数据出处）
  est_minutes, has_figure, figure_asset_id,
  source,                         -- 'real' / 'ai'
  generator_meta_json,            -- 生成参数、reviewer 记录
  content_hash, status            -- draft / reviewed / published / rejected
)

-- 知识点（树 + 跨边 + 闭包）
knowledge_nodes(id, parent_id, code, name, level, syllabus_ref, description, aliases_json, order_idx)
knowledge_edges(src_id, dst_id, rel, weight)          -- prereq / confusion / same_method
knowledge_closure(ancestor, descendant, depth)

-- 题–知识点（多对多，无主次之分）
question_knowledge(
  question_id, node_id,
  role,      -- 'main' | 'aux'，仅用于归因分摊，不用于组卷筛选
  weight,    -- 100 / 50，判卷后把失分按权重摊到各知识点
  PRIMARY KEY (question_id, node_id)
)

-- 作答记录
attempts(id, device_id, paper_id, question_id, answer_raw,
         score, max_score, score_rate, rubric_json, error_tags_json,
         duration_sec, created_at)     -- score_rate 用于跨卷对比

-- 错题本（掌握度驱动复习）
wrong_book(device_id, question_id, first_wrong_at, mastery, next_review_at,
           review_count, last_result)

-- 变式关系（错题 → 变式 → 是否迁移成功）
variant_links(src_question_id, variant_question_id, reason)

-- AI 题举报（见 §7.1）
question_reports(id, question_id, device_id, reason, detail,
                 status, resolution, created_at, resolved_at)

-- 评测数据中心（公开页面的数据来源）
llm_calls(id, kind, model, prompt_hash, tokens_in, tokens_out, latency_ms, ok, reject_reason, created_at)
```

几个刻意的决定：

- **题目存 LaTeX，不存图片。** 存图片就没有检索、没有变式、没有难度分析；LaTeX 还能直接喂给模型。
- **真题与 AI 题同表同池。** 组卷时 `source` 只是一个过滤条件，判卷、错题本、统计全都不用写两套。但**前端必须强制标注**：真题显示「2023 真题」+ 年份，AI 题显示「AI 原创 · 已校验」。不标注 = 用户把仿真题当成真题做，这是信任崩塌的起点，也是 AIGC 合规要求。
- **`status` 状态机是硬约束。** 只有 `reviewed` 才能进组卷池，这是防止「reviewer 形同虚设」的工程手段。
- **`llm_calls` 独立成表。** 出题通过率、打回原因分布、判卷耗时——这些是评测数据中心的数据来源。`model` 字段记录实际调用的模型，用于区分生成模型与判卷模型的表现。
- **一道题可以连多个知识点，且不分主次。** 组卷时按「任意关联」筛选，不按 `role` 筛选。反例：一道「用拉格朗日中值定理证明不等式」的题，若强行标一个 primary，用户选另一个知识点时这道题就会被漏掉。`role` / `weight` 只服务于判卷后的归因分摊。
- **一个大题就是一道题。** 按题号切分，题号下的所有小问 `(1)(2)` 都保留在同一题内，放进 `sub_items_json`，不拆成独立题。例如 2026 年最后一题是一个解答题、两问，切出来仍是一道题。这样不需要判断「是否共享题干」，也不会出现拆开后题干缺失的无解题目。
- **计数按题号算。** 用户选「5 道解答题」，一个带两小问的大题算 1 道。否则「5 道」变 8 个小问，和预期不符。

### 3.4 知识点树（完整版，已按 2027 大纲核实）

**结构是三层树：2 门 → 11 章 → 124 个考点。** 不是只有章名——章名只能做粗粒度筛选，打标和诊断都需要考三级节点。

不要手写，用大纲生成再人工校准：

1. 从大纲 PDF 抽「考试内容」条目（实测可完整提取，6 页）
2. 让模型把「考点清单」拆成三级节点，**每个节点必须挂一条 `syllabus_ref` 指回大纲原文**（防止模型自由发挥、防止超纲）
3. 人工校准：一级/二级必须与大纲**逐字一致**，三级允许合并或拆分
4. 用 `prereq` 边把同一章内的节点连成 DAG

#### 数学二的边界（容易搞错，值得记一下）

数学二**不含**以下内容，题库里出现就是错的：

- 无穷级数（数一、数三有）
- 向量代数与空间解析几何
- 三重积分、曲线积分、曲面积分
- 概率论与数理统计（数二不考）
- 数一的「傅里叶级数」「场论」

打标时如果模型给某道题打了「级数」标签，说明它记混了科目，要打回。这个约束可以写进 prompt 作为负例。

#### 两个用途

**雷达图**：11 个章作为维度太多，屏幕上挤不下。建议按门 + 高频章聚合成 6–8 个维度（函数极限连续 / 微分学 / 积分学 / 多元微积分 / 微分方程 / 线代），用户一眼看懂薄弱在哪。这比「AI 分析了你的 124 个知识点」诚实得多，也更有用。

**前置关系**：`prereq` 边只在同一章内连，跨章的不连。因为考研的依赖关系基本是章内递进的（比如「等价无穷小」是「洛必达」的前置，但「行列式」不是「二重积分」的前置）。跨章硬连会产生大量无意义的边，反而干扰诊断排序。

#### 一个必须解决的缺口：用户不说叶子节点的名字

实测一下就知道问题有多大。把用户最常说的 13 个词拿去匹配 124 个叶子节点：

| 用户说 | 精确命中的叶子节点 | 包含该词的叶子节点 |
|---|---|---|
| 二重积分 | **0** | 4 |
| 极限 | **0** | 6 |
| 定积分 | **0** | 6 |
| 特征值 | **0** | 2 |
| 微分方程 | **0** | 10 |
| 中值定理 | **0** | 3 |
| 矩阵 | **0** | 21 |
| 向量 | **0** | 10 |
| 线性方程组 | **0** | 5 |
| 导数 | **0** | 8 |
| 积分 | **0** | 18 |

**没有一个能精确命中。** 原因是大纲的叶子节点是按「考点」切的，粒度很细（「二重积分的计算（极坐标）」），而用户说的是「题型 / 知识块」（「二重积分」）。

如果只做字符串匹配，用户说「二重积分类型题」会得到 0 结果——这是最典型的检索失败。

### 3.5 三层检索：别名层 → 树展开 → 查询改写

不能指望用户学会大纲的措辞，也不能把大纲改成用户的语言（大纲是权威依据，必须逐字对齐）。正确做法是在中间加一层。

```
用户输入："二重积分类型题"
        ↓
① 查询改写（LLM）      抽出 → 概念「二重积分」+ 意图「出题」+ 粒度「知识块」
        ↓
② 别名层（精确匹配）    「二重积分」→ node_id = 多元函数微积分学/二重积分相关节点
        ↓
③ 树展开（闭包表）      取该节点下所有叶子 → 4 个叶子节点
        ↓
④ 组卷（SQL）           WHERE node_id IN (4 个 id) AND qtype = ...
```

#### ① 别名层：`aliases_json` 的正确用法

表结构里已经有 `aliases_json` 字段，但要明确定义它的语义：

```json
// knowledge_nodes 的一行
{
  "id": "uuid-...",
  "name": "二重积分的计算（极坐标）",
  "level": 3,
  "aliases": ["二重积分极坐标", "极坐标二重积分", "用极坐标算二重积分"]
}
```

**关键规则：别名是「用户可能怎么说」，不是「同义词词典」。**

- 每个叶子节点配 2–5 个别名，来源是真题解析里的常见表述 + 教材习题标题
- **上层节点（章 / 节）也必须有别名**，因为用户说的「二重积分」实际上是指「二重积分这一整块」——它对应的是父节点，不是某个叶子
- 别名只用于**召回**，不用于精确判定。匹配到多个节点时交给下一步裁决

这一层的作用是**把口语映射到树上的某个节点**，然后用闭包表展开成叶子集合。所以「二重积分」这个词挂在父节点上，展开后自动得到 4 个叶子——用户不需要知道「直角坐标」和「极坐标」是两回事。

#### ② 粒度自适应：用户说多粗，就展开到多粗

这是这套设计最有价值的地方。同一个词在不同粒度下都是合法的：

| 用户说 | 命中节点 | 展开后的叶子数 | 候选题量 |
|---|---|---|---|
| 「二重积分」 | 多元函数微积分学下的二重积分节点 | 4 | 充足 |
| 「二重积分的极坐标计算」 | 直接命中叶子 | 1 | 较少，可能需要降级 |
| 「多元函数微积分」 | 整章 | 16 | 很充足 |

**顺带修正我上一轮的一个判断**：我算「平均每个考点 4 题，所以 15 题凑不够」——这个结论只对**叶子粒度**成立。用户实际说的多是粗粒度词（「二重积分」而不是「二重积分的极坐标计算」），展开后候选池是叶子的 4–16 倍。所以：

- **粗粒度请求（用户常态）→ 池子充足，30 题无压力**
- **细粒度请求（用户少见的精确说法）→ 池子薄，需要降级到父节点**

降级方向反过来了：不是往相邻难度档借，而是**往父节点升**（「极坐标二重积分」不够 → 扩到「二重积分」全部）。这比放宽难度更合理，因为用户对知识范围放宽的接受度远高于对难度错配的接受度。

#### ③ 查询改写：用户一句话往往包含多个考点

你说得对——**用户说的话一般不止一个考点**。这是设计里必须支持的核心场景：

```
"帮我出几道二重积分和微分方程的应用题，要有点难度"
        ↓ 改写为结构化槽位
{
  "concepts": [
    {"term": "二重积分", "node": "...", "expand_to": "subtree"},
    {"term": "微分方程的应用", "node": "...", "expand_to": "leaf"}
  ],
  "qtype": ["free_response"],
  "difficulty": "hard",
  "count": null,          // 未指定 → 追问或默认 5
  "intent": "compose_paper"
}
```

改写 prompt 要做四件事：

1. **抽概念**：一句话里可能有 1–3 个考点，全部抽出，不要只取第一个
2. **判粒度**：这个词对应树上的哪一层（章 / 节 / 叶子）
3. **识别隐含约束**：「有点难度」→ 难度档；「应用题」→ 可能同时是知识点（微分方程的简单应用）和题型提示
4. **识别缺失槽位**：数量没说就追问，不要瞎猜

**改写失败要有兜底**：如果模型给出的概念在树里找不到，退回到别名模糊匹配 + 向量 Top-5，让用户从候选项里点选。不要静默返回空结果。

#### ④ 为什么这层不能用向量替代

一个直觉性的反问：既然要做语义匹配，为什么不直接向量检索？

因为**用户的口语词和叶子节点之间不是「语义相似」关系，而是「包含 / 上下位」关系**。「二重积分」和「二重积分的计算（极坐标）」在向量空间里确实很近，但向量检索会同时返回「定积分的计算」「三重积分」这些同样近的邻居——它不知道「二重积分」是那 4 个叶子的**父概念**。

而树结构知道。所以：**别名层 + 闭包表负责「准确展开」，向量只负责「别名也没命中时的模糊兜底」。** 顺序不能反。

### 3.6 向量层的三个位置

| 位置 | 干什么 | 怎么做 | 规模 |
|---|---|---|---|
| **意图映射** | 用户说「帮我练练拉格朗日」，映射到 `node_id` | 先用 §3.5 的别名层 + 闭包表；别名没命中时才走向量 Top-5 + 模型裁决 | 137 节点 |
| **去重** | 新生成的题不能和题库/本卷重复 | 题干嵌入余弦相似度 > 0.9 打回 | ~500 条 |
| **相似题推荐** | 错题旁边推「同类真题」 | 见 §3.6.1 | ~500 条 |

**关键判断：向量只负责「把用户的话翻译成 ID」和「找长得像的题」，不负责「把题目按条件找出来」。** 后者是 SQL 的事。

工程上要注意：Qoder Sites 的数据库迁移只允许 `CREATE TABLE` / `ALTER TABLE ADD COLUMN` / `CREATE INDEX` 三类语句，**不要假设能装 pgvector**。上面的规模（137 + 500 条向量）在应用层用余弦相似度算完全够，甚至不需要索引结构。这个约束反而逼出了正确的设计。

#### 3.6.1 相似题推荐怎么做

先说清楚**这个功能要解决什么**：用户做错一道题，除了看解析，还需要「再练几道同类的」来确认是偶然失误还是真不会。

朴素做法是「同知识点 + 同题型 + 同难度，随机抽 3 道」。这个够用，但有个明显缺陷：**它可能推荐一道「知识点相同但考法完全不同」的题**。比如错的是「用拉格朗日证明不等式」，推过来的却是「用拉格朗日求极限」——同一考点，练不到点子上。

所以推荐要**分两档**：

**第一档：结构召回（SQL，主路径）**

```sql
-- 候选集：共享至少一个知识点 + 同题型，排除已做
SELECT q.id, q.stem_latex, q.difficulty, q.score
FROM questions q
JOIN question_knowledge qk ON qk.question_id = q.id
WHERE qk.node_id = ANY(:wrong_q_nodes)      -- 错题挂的所有知识点
  AND q.qtype = :wrong_q_type
  AND q.id <> :wrong_q_id
  AND q.status = 'published'
  AND q.id NOT IN (SELECT question_id FROM attempts WHERE device_id = :dev)
LIMIT 30;
```

召回 30 道，然后用两个信号排序：

| 信号 | 权重 | 怎么算 |
|---|---|---|
| 知识点重合度 | 高 | 与错题共享的 `node_id` 越多越靠前；`role='main'` 的重合加权更高 |
| 难度接近度 | 中 | 与错题难度档相同得满分，相邻档减半 |
| 年份新鲜度 | 低 | 近 10 年优先（老题表述和现在差异大） |

**第二档：题干相似（向量，用于「找同款」）**

只有当用户明确点「找同类题」时才启用，做的是「找和这道题长得像的」：

```
错题题干嵌入 → 与全部题库算余弦相似度 → Top-20
    ↓ 用知识点标签做二次过滤（必须共享至少一个知识点）
    ↓ 再用难度档过滤（±1 档以内）
    ↓ 取 Top-3
```

**为什么向量要放在第二档而不是第一档**：向量擅长「这题和那题像不像」，不擅长「这题是不是我要的知识点」。而推荐的硬要求是后者。所以**用 SQL 保证正确性，用向量提升相关性**，顺序不能反。

**一个必须做的细节：推荐要能解释**

每条推荐旁边写一句理由，比如「同样考查拉格朗日中值定理，2021 年第 19 题」。理由从哪来？就是排序时的那个信号——知识点重合 + 难度接近。

这不是装饰。用户看到「为什么推这道」，才会相信推荐是有逻辑的，而不是随机塞题。这个细节在演示时很能说明工程完成度。

**冷启动问题**：如果错题挂的是冷门叶子（如「曲率」），结构召回可能不足 3 道。此时：

- 不足 3 道 → 往父节点升（§3.5 ② 的同一逻辑）
- 仍不足 → 降级为「AI 生成 2 道同考点变式」，走 §5.6 的 reviewer 流程
- 都失败 → 显示「该考点真题较少，建议直接看解析」，**不要硬凑**

**与 §7 变式生成的区别**（容易混）：

| | 相似题推荐 | 变式生成 |
|---|---|---|
| 来源 | 题库里已有的真题 | AI 新生成 |
| 触发 | 判卷后自动出现 | 用户主动点「出变式」 |
| 目的 | 巩固考点 | 防止背答案 |
| 成本 | 零 | 一次 LLM 调用 + 审核 |

两者都出现在错题旁边，但**推荐在前（免费、即时），变式在后（用户主动要）**。

## 4. 题库构建流水线（替代 OCR）

### 4.1 七步

```
① 坐标抽取    PyMuPDF 取每页 span（文字 + bbox + 字号 + 字体）
       ↓
② 题目切分    按 section 标题 + 题号 + 与 873 张卡对账
       ↓          按题号成题，题号内的小问进 sub_items
③ LaTeX 还原  模型把「带坐标的碎片」重组成 LaTeX（分式/矩阵/积分限靠 y、x 坐标）
       ↓
④ 答案对齐    从答案速查取客观题答案、从详解取解答过程，按 (年份, 编号) 对齐
       ↓
⑤ rubric 提炼 解答题从参考解答反推评分步骤（官方不公布细则，必须自建）
       ↓
⑥ 难度标注    三档，双评 + 锚定；记录 difficulty_source
       ↓
⑦ 校验入库    渲染回图片与原页视觉比对 + 知识点打标 + 抽检 10%
```

**真题和 AI 仿真两条路径都要跑这条管线**，区别只是答案与 rubric 的来源（真题是外部对齐 + 反推，AI 题是生成时同步产出）。

### 4.2 每一步的坑（都已实测确认）

**① 坐标抽取**：`get_text("dict")` 能拿到每个 span 的精确 bbox，这是重建公式的唯一依据。不要用 `get_text()` 的线性输出。

**② 题目切分**：不要自己数题号，用卡包对账。873 张卡的标签已经给出了 `year + type + 序号`，你只需要保证「每年题数一致、每题能对上」。对不上就说明切分错了，比人工逐题核对快一个数量级。

**③ LaTeX 还原**：这是唯一需要模型的一步，也是唯一需要认真设计 prompt 的一步。要点：

- 给模型**不是纯文本，而是带 `(x0,y0,x1,y1)` 的片段列表**，并在 prompt 里说明「同一 x 区间、y 相邻的两段是分数」
- 分年批量，一年一次调用（一年 20 来题，上下文够）
- 输出严格 JSON：`[{seq_label, qtype, stem_latex, options, has_figure}]`
- 温度调低；对同一份输入跑两次，比对差异，差异大的题人工看

**④ 答案对齐**：答案速查里解答题写的是「见解答末尾结论」，所以要准备两个来源——速查取客观题答案，详解取解答题完整过程。实测 1987 年答案页格式规整（题号 + 答案两列），可以结构化解析。

**⑤ rubric 提炼**：官方从不公布评分细则，解答题的评分步骤必须从参考解答反推。这是「判卷」能否成立的关键前提，不是可选项。

**⑥ 难度标注**：三档双评 + 锚定（见 §5.5），记录 `difficulty_source`。

**⑦ 校验**：把还原后的 LaTeX 用 KaTeX 渲染成图片，与原 PDF 页面同区域做视觉比对。人工抽检 10%（约 50 题），错误的题修正后把修正样本回灌到 prompt 里。

### 4.3 一个必须提前想清楚的问题：版权

试卷与答案的原始著作权不属于仓库作者（仓库代码是 MIT，内容不是）。参赛作品的合规做法：

- 站内**不提供原卷 PDF 下载**，只呈现结构化后的题目文本
- 每题标注来源年份，页面注明「题目整理自公开真题，著作权归原权利人」
- 演示视频里展示「数据来源」而不是「数据搬运」
- 论坛帖如实说明数据处理流程

这件事写进计划，比事后被问起来强。

## 5. 出题引擎

### 5.1 三选一的题源，一套流程

「真题 / AI 仿真 / 混合」不是三条独立流程，而是同一个组卷器上的一个开关。区别只在 `questions.source` 是 `real` 还是 `ai`，判卷、错题本、统计全部共用。

```
题源：◉ 真题   ○ AI 仿真   ○ 混合
筛选：知识点 · 题型 · 数量 · 难度档 · 年份区间 · 排除已做
        ↓
   同一个组卷器 → 同一份试卷结构 → 同一套判卷
```

真题不是「还原某一年整卷」，而是**跨年份按知识点和题型抽题重排**——用户要的是练真题的「题」，不是做一份历史考卷。原卷还原没有产品价值，市场上到处都能买到。

**重排不是纯随机**，必须满足三个约束，否则用户一眼就能看出是拼凑的：

1. **考点去重**：同一知识点不能连出两道（用 `question_knowledge` 的关联判断，不限 role）
2. **难度梯度**：见 §5.5 的两种模式
3. **题型顺序**：选择在前、填空居中、解答在后

### 5.2 三种题源模式

| 模式 | 组成 | 适用场景 | 失败兜底 |
|---|---|---|---|
| **真题** | 100% 真题抽题 | 想知道真实考过什么 | 池子不足时降级到相邻难度档 |
| **AI 仿真** | 100% AI 生成 | 想练没见过的新题、真题不够用时 | 生成失败则换真题 |
| **混合** | 真题为主，AI 补足缺口 | 日常练习的默认选项 | 见下 |

**混合模式的配比规则：真题 : AI = 1 : 1**（已定）。

```
① 按用户条件抽真题，目标数量 = ⌈总题数 / 2⌉
② 真题够 → 交付；不够 → 用现有的全部真题
③ AI 生成剩余缺口，走完整 reviewer 流水线
④ 卷首显示实际比例：「本卷 8 题真题 + 7 题 AI 原创」
```

为什么 1:1 是合理默认：**真题保真度 + AI 题新鲜度各占一半**，用户既能确认自己练的是真实考点，又能避免「这些题我都见过」。而且 1:1 让「真题 / AI 分开报得分率」这个质量信号更可靠——两部分样本量接近，比较才有意义。

**配比是目标，不是硬约束**：真题不够时按实际数量给，不为了凑 1:1 而少给真题。卷首必须显示实际比例，不能让用户以为拿到的是 1:1。

**题目数量上限 30 题**（已定，所有模式共用）。这个上限有实际意义：单卷超过 30 题，用户一次做不完，完成率会崩。

**候选池够不够，取决于用户说的粒度，不取决于叶子节点的题量。** 这里我上一轮算错过，修正一下：

- 501 题 ÷ 124 个叶子 ≈ **平均每叶子 4 题**——但这是**叶子粒度**的数字
- 用户实际说的多是粗粒度词（「二重积分」「微分方程」），经 §3.5 的树展开后是 4–16 个叶子合并，候选池放大 4–16 倍
- 所以**用户常态下的请求，30 题完全够**
- 只有用户说出精确的叶子名（「二重积分的极坐标计算」）时池子才薄，此时**往父节点升**（§3.5 ②），而不是放宽难度

**真正的冷门叶子仍然存在**（曲率、弧微分、施密特正交化、惯性定理，22 年只考过 2–5 次）。这类请求确实要靠 AI 补——这正好是混合模式的价值，不是缺陷。

混合模式必须满足 §5.3 的强制标注：同一张卷子里真题和 AI 题混排，每道题都要标清来源。整卷统计也按两部分分开报。

### 5.3 来源标注（强制，不是可选项）

AI 题与真题同池，但**用户必须一眼看出区别**：

| 题源 | 题号旁的标注 | 说明 |
|---|---|---|
| 真题 | `2023 真题 · 第 15 题` | 显示年份，可追溯 |
| AI 原创 | `AI 原创 · 已校验` | 明确告知非真题 |

三条硬规则：

- **同一张卷子里混排时，标注必须在题号同一行**，不能藏在折叠区或页脚
- **AI 题不能伪装成真题**。不写年份、不模仿「××年第××题」的编号格式——这是 AIGC 合规的基本要求
- **整卷统计要分开报**：得分率按「真题部分 / AI 部分」分别给。混在一起算会掩盖一个事实：用户可能在真题上得分低、在 AI 题上得分高，说明 AI 题难度标偏了

> 这个标注同时是个产品卖点。大多数「AI 出题」产品不会主动区分，用户做完了都不知道自己练的是不是真题。主动标注反而是专业度。

### 5.4 两种组卷模式（用户显式选择）

| 模式 | 用户看到的话 | 卷内难度结构 |
|---|---|---|
| **整卷模考** | 「本卷难度按 易→中→难 梯度分布，整体定位为【中】」 | 按 3:5:2 配比铺开，同一题型内递增 |
| **专项突破** | 「本卷全部为【中】档题，适合集中突破」 | 单档位，允许全卷同难度 |

**为什么必须区分**：档位本身不产生梯度，排序才产生梯度。用户选「中」，如果六道解答题全部是「中」，做起来是平的，和「像真题」这个卖点直接冲突。真实卷子是梯形分布的。

**分值照实显示，不重分配。** 拼出来的卷子是多少分就是多少分——用户自己选了题型和数量，本来就知道。这省掉一层解释成本，也避免「你凭什么改分值」的质疑。

两个连带影响：

- **成绩单必须给得分率，不能只给得分。** 113 分的卷子考 90 分（79.6%）和 150 分考 90 分（60%）不是一回事。跨次对比只有得分率有意义。
- **计时按比例折算**：默认 1.2 分钟/分（对标 180 分钟 / 150 分），允许用户改。

### 5.5 难度：三档 + 得分率区间

用「易 / 中 / 难」三档，不用连续系数。理由不是「模型方便」，而是**三分类的标注一致性远高于连续打分**——模型打 0.53 还是 0.57 基本是噪声，但判「易/中/难」时分歧小得多。

**口径采用教育测量的标准定义**：难度系数 = 平均分 ÷ 满分（得分率），数值越大越容易。UI 上写「易 / 中 / 难」，旁边标注对应的得分率区间。

> 注意：不要直接套用通用教学测量区间（易 0.7–0.9 / 中 0.5–0.7 / 难 0.3–0.5）。考研数学整体得分率约 0.45–0.55，直接套用会把大部分真题判成「难」，「中」几乎为空。区间要用**自己题库的实测数据**标定，或改用「卷内相对分位」（易=前 30% / 中=中间 50% / 难=后 20%），后者不依赖绝对值且天然对齐 3:5:2 的命题惯例。

**锚定标注**：给模型 5–10 道已有难度标注的真题做 few-shot 参照，让它做相对判断，比绝对打分可靠。锚点数据可来自第三方教研机构的真题难度分析，但**必须记录来源**（`difficulty_source`），评审问「依据是什么」时要能答出出处。锚点要按题型分别给——同一题放在选择里和解答里，难度感受不同。

**审计规则（双评）**：

- 出题者判一档，审核者独立判一档
- 分歧 ≤ 1 档 → 取较难的那档（保守，避免把难题标简单）
- 分歧 = 2 档（一说易一说难）→ 打回重判，这通常说明题目本身有问题
- 一致性指标用 **Cohen's Kappa**，不要用百分比一致率（后者会被「都判中」刷高）

**难度是活的**：初始难度是模型估的，用户做题后就有了真实得分率。`difficulty_obs` 记录实测值，样本少先信估计、样本多信实测（收缩估计）。这正是考试院计算难度系数的方法，演示时是个好点——难度不是贴上去的标签。

**候选池降级链**——顺序很重要，**先放宽知识范围，再放宽难度**：

```
用户说「二重积分的极坐标计算」，要 10 道「难」题
  ↓ ① 知识点往父节点升（→ 二重积分全部，4 个叶子）
  ↓ ② 仍不够 → 再往上升一级（→ 多元函数微积分学）
  ↓ ③ 仍不够 → 放宽难度档（难 → 中）
  ↓ ④ 仍不够 → 询问用户是否用 AI 生成补足
```

**为什么知识范围优先于难度**：用户对「范围放宽」的接受度远高于「难度错配」。说好要难题却给了中等题，用户会觉得系统不听话；范围从「极坐标」扩到「二重积分」，用户通常没意见——毕竟都是同一块内容。

降级必须**告知用户**，不能静默换题。另外：真题里高难度题本就稀薄（按 3:5:2 惯例，难档只占 20%），高难度请求基本要靠 AI 生成补——这反而是个好故事：真题覆盖中段，AI 补两端。

### 5.6 Reviewer 流水线（仅 AI 生成路径）

真题不需要生成，但**解答题需要 rubric**：官方只公布参考解答，从不公布评分细则。所以两条路径都要跑离线管线，区别只是答案来源。

你的设想是「交给下一个 reviewer 再做一遍确保题目都能做」。方向对，但**只做一遍不够**：同一个模型用同一个 prompt 复算，会犯同样的错，这叫自一致性陷阱。需要三层，缺一不可：

```
         ┌─────────────┐
种子 ───▶ │ ① 出题者     │ 题干 + 答案 + 解析 + 知识点标签 + 难度档位
（知识点 │  Generator  │
 + 真题   └──────┬──────┘
 few-shot）      ▼
         ┌─────────────┐
         │ ② 盲解者     │ 只给题干，不给答案；不同 prompt 角色、
         │  Blind Solver│ 不同温度（有条件就换模型）
         └──────┬──────┘ 输出完整步骤 + 最终答案 A'
                ▼
         ┌─────────────────────────────────────┐
         │ ③ 审核者 Auditor（8 项 checklist）   │
         │  □ 可解性：A' 是否收敛到确定答案      │
         │  □ 一致性：A 与 A' 符号等价（SymPy）  │
         │  □ 唯一性：选择恰一正确；填空答案规范  │
         │  □ 不超纲：对照 syllabus_ref         │
         │  □ 不偏题：考查点是否就是目标知识点    │
         │  □ 难度：双评一致（见 §5.5）          │
         │  □ 不重复：与题库/本卷相似度 < 0.9    │
         │  □ 表述：无歧义、条件充分、无陷阱     │
         └──────┬──────────────────────────────┘
         全过   │   任一失败
         ┌──────┴──────┐
         ▼             ▼
    status=reviewed  带失败原因回炉（≤2 次）→ 仍失败则换真题兜底
                    （原因写入 llm_calls，供评测数据中心）
```

**入库的是验证后的答案，不是出题者的初版。** 出题者给 A，盲解者算出 A'，不等价就打回。最终 `answer_source` 必须标记 `ai_verified`，不能标 `official`。

**第三层里最有价值的是「可执行校验」**：能用 SymPy 算的题（求极限、积分、极值、方程组），直接代入验证答案，这是唯一不依赖模型自觉的检查。它会抓住「答案算错」这一类最高频的错误。演示时这一个细节就能说明「我们不是随便调个 API」。

**建议设定的量化目标**（也是评审会问的）：一次通过率 ≥ 70%，盲解与出题答案一致率 ≥ 90%，重复率 0。达不到就说明 prompt 还得改。

### 5.7 试卷的存储形态：不存文档

**试卷存成「题目 ID 列表 + 结构模板」，不存 PDF / DOCX / HTML 快照。**

```
paper = { mode: 'exam' | 'drill', sections: [
  { type: 'choice', score: 5, items: [q_id, ...] },
  ...
]}
```

渲染交给前端（KaTeX）。这样同一份试卷可以：屏幕作答、打印、逐题回看解析、重新组卷。存成文档就把这些能力全部锁死。

**为什么不做 PDF / Word**：

- **交互是核心价值。** 答题、计时、判卷、解析展开、错题一键收录，PDF 全做不到。只出 PDF 产品就退化成「出卷工具」，在 StudyHack 赛道讲不出差异。
- **服务端生成 PDF 在 Sites 上做不了**：Edge Function 是 Deno 环境，没有 LaTeX 引擎也没有无头浏览器，平台不允许部署期装依赖。
- **打印需求用 CSS 解决**：加 `@media print`，用户点打印后「另存为 PDF」，KaTeX 已渲染内容打印质量足够。零依赖零成本。
- **不做 Word**：数学公式是 OMML，LaTeX→OMML 链路脆弱（pandoc、字体缺失、公式错位），收益极低。

**关于「导出 LaTeX 源码」：建议不做。**

我上一版说「成本几乎为零」，这个理由是错的——虽然题库确实存 LaTeX，但导出意味着要做：试卷级的 LaTeX 模板拼装、宏包依赖处理、编译说明。用户拿到一个 `.tex` 文件却编译不过，体验比不给更差。而目标用户里会用 LaTeX 编译试卷的，可能不到 1%。

**真正需要「拿走」的场景，用打印就够了**：`@media print` + 浏览器「另存为 PDF」，得到的是排版好的 PDF，而不是需要自己编译的源码。这才是用户实际想要的。

如果确实要保留一个「导出」入口，建议做**导出为 Markdown 或纯文本**（题干 + 选项 + 答案 + 解析），用于整理笔记、贴到自己的文档里。这个成本真的接近零，也不需要用户会 LaTeX。

### 5.8 出题 prompt 的结构化约束

生成必须输出严格 JSON，字段固定（题干、小问、选项、答案、解析、知识点、难度档、预计耗时、考查能力）。不要让它输出「漂亮的一整张卷子」——前端需要的是数据，不是文本。

## 6. 判卷引擎

### 6.1 两条判卷路径与答案来源

判卷按题型分流，但**答案来源必须记录清楚**，这是用户信任的基础：

| 题源 | 客观题答案 | 解答题评分依据 | `answer_source` |
|---|---|---|---|
| 真题 | 答案速查（官方） | 从官方参考解答反推 rubric | `official` / `rubric_derived` |
| AI 仿真 | 审核通过后的答案 | 出题时同步产出 rubric | `ai_verified` |

**必须说清的一个限制：考研官方只公布参考解答，从不公布评分细则。** 所以「按真题答案判卷」对选择题成立，对解答题不成立——一份 10 分的解答题，官方给的是完整推导，而「用户写到哪一步该给几分」必须自己从参考解答反推出来。评审问「判卷依据是什么」时要能这样答：客观题用官方答案，解答题用自建 rubric（按步骤给分，可申诉）。

### 6.2 分题型策略

| 题型 | 方法 | 注意 |
|---|---|---|
| 选择 | 选项比对 | 简单，但要处理「多选漏选」 |
| 填空 | **SymPy 等价化简后比较**，多解按集合比 | 不能字符串比较：`\frac{1}{2}` / `0.5` / `\dfrac12` 是同一个答案 |
| 解答 | 分步 rubric，模型逐步判定是否达成 | 见下 |

### 6.3 解答题的分步 rubric

题目入库时预生成评分点（真题从参考解答反推，AI 题生成时同步产出），形如：

```json
{
  "max_score": 10,
  "rubric": [
    {"step": 1, "desc": "正确写出拉格朗日函数", "points": 3, "must": true},
    {"step": 2, "desc": "求偏导并令其为零", "points": 3},
    {"step": 3, "desc": "解出驻点", "points": 2},
    {"step": 4, "desc": "验证并得出结论", "points": 2}
  ]
}
```

判卷时模型必须**引用用户原文片段**来证明某一步达成，不允许只给结论。总分取 `min(步骤得分之和, 满分)`。这样做的两个好处：分数可解释（用户能申诉）、演示时可复现（同样的作答必然同样的分）。

### 6.4 作答输入方式：拍照手写（已定）

**用拍照 + 多模态模型识别手写。** 键盘输入数学公式对考研学生不现实——一道解答题要敲十几个分式、积分号、上下标，输入成本远高于手写，用户会直接放弃。

流程：

```
拍照/上传 → 图像预处理（裁边、增强、纠偏）→ VLM 识别为 LaTeX
       → 用户在「识别结果」上可编辑修正 → 提交判卷
```

**关键设计：识别结果必须让用户确认或修正。** 不能识别完直接判卷——手写识别有误差，一旦识别错导致判错，用户会认为「判卷不准」，而这个锅其实是识别环节的。让用户看一眼 LaTeX 再提交，既救了准确率，也把责任边界划清楚了。

**分题型处理**：

| 题型 | 输入方式 | 说明 |
|---|---|---|
| 选择 | 点选选项 | 不需要手写 |
| 填空 | 拍照或简单文本 | 答案通常很短，两种都行 |
| 解答 | 拍照手写 | 必须，过程分依赖完整步骤 |

**必须做的风险预案**：手写识别是整条链路最不稳定的一环。要准备一条降级路径——识别失败或用户不满意时，允许切到文本输入兜底（不是主路径，但要有）。演示时提前准备几份「识别效果好」的样例作答，不要现场手写。

**识别质量要有量化指标**：抽 30 份手写作答做人工比对，算出「公式级识别准确率」。评审问「拍照识别准不准」时，拿数字答比说「还行」强得多。

### 6.5 整卷诊断

**成绩一律以得分率呈现**（得分 ÷ 卷面总分），因为拼出来的卷子分值各不相同，跨次对比只有得分率有意义。

- 按 6 个聚合维度算得分率 → 雷达图（维度划分见 §3.4 末尾：函数极限连续 / 一元微分学 / 一元积分学 / 多元微积分 / 常微分方程 / 线性代数）
- 薄弱点排序时加**前置惩罚项**：如果某考点的 `prereq` 也没掌握，权重上调（这是图结构第二次真正产生价值）
- 输出三条可执行建议：先补哪个点、做几道什么题、几天后复查

**一个口径陷阱**：一道题连了两个知识点时，失分不能在各知识点分母里重复计。雷达图各轴独立算没问题，但「整卷得分率」只能按题目自身分值算，不能从知识点维度反推——否则各知识点得分率之和会超过 100%。

## 7. 错题本与定期抽题

**错题本**：自动收录，字段是「题目 + 你的作答 + 错因标签 + 掌握度 0–5 + 下次复习时间」。错因标签由判卷产出：概念不清 / 计算失误 / 方法不对 / 审题偏差 / 表达不规范。

**错题旁的两个出口**（顺序有讲究）：

1. **相似题推荐**（自动出现，零成本）——从题库里找同类真题，逻辑见 §3.6.1
2. **主动出变式**（用户点击，需生成）——以错题为种子，生成「同知识点、同题型、不同参数或情境」的新题，走 §5.6 的完整 reviewer 流程

先免费后付费：用户做错题后立刻能看到 3 道同类真题，不需要等生成、不消耗额度。变式是「真题都做完了还想练」时的进阶选项。

**定期抽题（避免背答案）**——这是你设想里最好的一个点，建议这样落地：

- 简化 SM-2：掌握度映射间隔 `[1, 2, 4, 7, 15, 30]` 天
- 到期不直接给原题，**先给变式**；变式答对才 `mastery + 1`
- 原题只在 `mastery ≥ 3` 时才复现，用于确认不是「记住了套路」
- 答错 `mastery - 1` 且重置到 1 天

这条规则直接对应「防止背答案」的产品承诺，也能在演示里做成一个很直观的动画。

### 7.1 AI 题举报与下架（已定）

公共题库里的 AI 题是所有人共用的，所以必须有一个纠错出口。

**流程：用户举报 → 你手动复核 → 下架或修正，不做自动下架。**

- 每道 AI 题旁有「这题有问题」入口，理由选项：答案错误 / 题目无解 / 表述有歧义 / 超纲 / 与真题重复
- 举报写入 `question_reports` 表，`status` 从 `published` 转为 `pending_review`（**立即从组卷池移除**，不等复核）
- 你从后台看举报列表，逐条判定：修正后重新发布，或永久下架
- **不做自动下架**：自动下架会被恶意举报滥用，而且误判的成本比晚修一会儿高

```sql
question_reports(
  id, question_id, device_id, reason, detail,
  status,            -- open / resolved / rejected
  resolution,        -- 'fixed' / 'removed' / 'no_issue'
  created_at, resolved_at
)
```

关键设计：**举报即隐藏，复核即裁决**。前者保护后续用户不再遇到坏题，后者防止误伤。这个先后顺序很重要——等复核完再隐藏，中间可能已经有几十个用户做了错题。

## 8. Agent 化：把闭环做成 tool

对话层不做「让模型生成整张卷子」，做「意图路由 + 槽位填充 + 调工具 + 渲染结果」。工具清单：

| 工具 | 入参 | 出参 |
|---|---|---|
| `resolve_concepts` | 自然语言（可含多个考点） | `[{term, node_id, level, expand_to, leaf_ids[], candidate_count}]` |
| `search_knowledge` | 自然语言 | `[{node_id, name, path, score}]`（`resolve_concepts` 失败时的模糊兜底） |
| `list_knowledge_tree` | parent_id | 子节点列表 |
| `compose_paper` | 知识点（可多个）/题型/数量/题源/模式/难度档 | `paper_id` + 题目摘要 |
| `get_paper` | paper_id | 完整试卷（LaTeX） |
| `submit_answers` | paper_id + 作答 | 逐题得分 + 解析 + 诊断 |
| `get_weakness_report` | 时间范围 | 雷达图数据 + 薄弱点 |
| `list_wrong_questions` | 筛选条件 | 错题列表 |
| `generate_variant` | question_id + 数量 | 变式题（已过审） |
| `schedule_review` | — | 今日待复习清单 |

**`resolve_concepts` 是对话入口的关键工具**（对应 §3.5 的三层检索）。它返回的不只是节点 ID，还包含 `leaf_ids` 和 `candidate_count`——这样模型在调 `compose_paper` 之前就知道「二重积分能出 40 道题」还是「这个细粒度考点只有 3 道」，可以主动调整数量或提示用户。

**多考点是一等公民**：`compose_paper` 的知识点入参是数组，不是单个值。用户说「二重积分和微分方程的应用题」时，组卷器要在两个子树之间分配题量，并保证不出现「五道题全是二重积分」这种失衡。

**三个必须遵守的工程约定**：

1. **工具返回结构化数据，前端用组件渲染题目卡片。** 不要让模型把题目正文念出来——token 爆炸、格式失控、无法交互。
2. **写操作前弹确认卡片。** 模型调用 `compose_paper` 后先展示「即将生成：极限 3 题 + 中值定理 2 题，真题模式」让用户确认，避免「我说错一句它就出了 20 道题」。
3. **意图不明确时降级为追问，不要猜。** 「帮我练练数学」→ 追问「哪个章节？」而不是随机出一套。

## 9. 用户画像与人格

保持极轻，**人格只影响语气层，不影响出题与判卷逻辑**（否则评测不可控、结果不可复现）。

```json
{
  "subject": "math2",
  "target_score": 120,
  "level": "基础一般",
  "daily_minutes": 90,
  "exam_date": "2026-12-26",
  "persona": "strict_coach"   // strict_coach / warm_senior / blunt_senior
}
```

人格实现方式：在 system prompt 里注入一段「语气规范」，工具调用、评分标准、rubric 完全共享。这样换人格不会导致同一份答卷分数变化——这个一致性本身值得在演示里讲一句。

存储：**不做登录鉴权**（已定）。用户画像、作答记录、错题本都挂在浏览器生成的匿名 `device_id` 上，同时支持导出/导入 JSON。

**这个决定的代价必须写清楚**（不是反对，是让你和队友知道边界在哪）：

- **换设备 = 数据丢失。** 清缓存、换浏览器、换手机，学习记录全部消失。必须提供显眼的「导出备份」入口，并在首次使用时提示一次。
- **`device_id` 不是身份，是标签。** 它是浏览器生成的，用户可以随意伪造。所以任何写入都必须由服务端按 `device_id` 做归属校验，不能因为「没有登录」就放开写权限。
- **AI 生成题的公共池要防刷。** 无登录意味着任何人都能触发 LLM 生成，成本敞口是真实存在的。必须做：按 `device_id` 的每日生成配额 + 全站总量上限 + 结果缓存复用。

这三个代价在 demo 场景下都可接受，但**如果之后要扩展成真实产品，登录是第一件要补的事**——因为学习数据一旦丢失，用户不会给第二次机会。

## 10. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 前端 | React + Tailwind + **KaTeX** + Recharts | 数学渲染是刚需；KaTeX 比 MathJax 快，适合移动端 |
| 后端 | Qoder Sites function backend（database + functions + storage） | 赛事要求部署在 Sites；密钥必须留在服务端 |
| 数据库 | 托管 PostgreSQL（见 §3.3） | 迁移 DDL 受限，按「无扩展」设计 |
| 图片资产 | Sites storage（图形题裁切图、作答照片、渲染比对图） | 题目正文不进 storage |
| 离线管线 | Python 3.11 + PyMuPDF（本地已装） | 只在开发期跑，不在线上跑 |
| 生成模型 | 强模型（题目质量要求高） | 出题是产品核心，不能省 |
| 判卷模型 | 与生成**分开**（已定），可与生成同源但用不同 prompt/温度 | 降低自一致性错误：生成者与盲解者若是同一模型同一 prompt，会犯同样的错 |
| 识别模型 | 多模态 VLM | 手写公式识别 |
| 评测集 | 50 题人工金标（答案 + 知识点 + 难度） | 用来算通过率/一致率，也是答辩数据 |

> 一个提醒：Qoder Sites 是公网可访问的（访问策略 public），意味着**任何人都能打你的函数**。无登录方案下这一点更严重——LLM 调用必须做速率限制和成本上限，否则链接发出去就可能被刷爆。这件事在 D10 联调时必须做。

### 10.1 平台能力与硬约束（已核对本机 Sites 插件文档）

Sites **不是只能做静态页**，它提供完整后端：

| 能力 | 提供什么 | 项目里怎么用 |
|---|---|---|
| 服务端逻辑 | 一个 `app` Edge Function（Deno，`index.ts` 的 HTTP handler） | 组卷、判卷、调模型、错题本读写 |
| 数据库 | 托管 PostgreSQL，Function 侧 Supabase 适配器 | 题库、知识点树、作答记录 |
| 文件存储 | 平台 Storage（Function 内 `import { storage } from './_qoder/storage.mjs'`） | 图形题裁切图、渲染比对图 |
| AI | Qoder Cloud Agents，平台注入 `QODER_PAT` | 出题、盲解、审核、判卷 |
| 访问 | 公网 public，浏览器同源调 `/functions/v1/app` | 评委直接打开就能用 |

但有几条硬约束，直接影响架构：

**1. 只有一个 Function，所有接口走它。** 不是「一个接口一个函数」，而是单个 `app` 入口内部路由分发（`/functions/v1/app?action=compose`）。组卷、判卷、生成必须共享一个部署单元，不能按微服务拆。

**2. 数据库 DDL 是受限子集，不是完整 PostgreSQL。** 只允许 `CREATE TABLE` / `ALTER TABLE ADD COLUMN` / `CREATE INDEX`；列类型只支持 `boolean / integer / bigint / text / uuid / timestamptz / jsonb`。落地影响：

- 没有 `numeric` → 分数用 `integer`（按半分制存 x2，或直接存整数分）
- 没有 `date` → 日期存 `text`，格式在 Function 里校验
- 没有数组类型 → 标签、选项、小问列表存 `jsonb`
- 没有 `CHECK`、没有自定义函数/触发器 → 约束逻辑写在 Function 里
- **没有 pgvector** → 向量在应用层算（§3.6 的设计正好符合）

**3. 没有定时任务。** Function 是请求驱动的 HTTP handler，不能起常驻后台进程。所以「定期抽题」不做成服务端 cron，而是**用户打开时按 `next_review_at` 查一次「今日待复习」**。这反而是更对的设计：没有常驻进程，就没有「服务停了提醒全丢」的问题。

**4. 函数执行时长没有公开数值。** 文档只说要「实测部署后的限制」。这里有个真实风险：**一道题的「出题→盲解→审核」三趟 LLM 调用很可能超过单次请求时限**。缓解：每次只生成 1–2 题、用 SSE 推进度、或拆成「提交任务 → 轮询结果」两段。必须在 D6 之前用真实部署量出来，不能假设。

**5. 题库导入不走线上。** 501 道题（2005–2026）的解析管线在本地跑 Python，结果通过管理接口批量灌入（单次 1–100 行）。这是「离线管线 + 线上只读」的结构，顺带解决了版权问题——原卷不上服务器。后续扩展到 1987–2004 只是重跑管线，架构不用改。

**6. 启用 AI 能力需要你确认一次。** 平台会自动为账号创建 Qoder PAT 并注入服务端。正式开工前我会先问。

### 10.2 评测数据中心（公开页面，已定）

所有用户可访问，不需要登录。这是把「AI 出题不可靠」这个最大质疑变成专业度的地方——主动公开指标，比让评委猜要强得多。

**展示什么**（全部从 `llm_calls` 与 `attempts` 聚合，只读）：

| 指标 | 口径 | 为什么值得展示 |
|---|---|---|
| 题库规模 | 真题 501 / AI 原创 N，按年份和知识点分布 | 证明题库不是空壳 |
| 出题一次通过率 | `ok=true` ÷ 总生成次数 | 最核心的质量指标 |
| 打回原因分布 | `reject_reason` 分类占比 | 证明 reviewer 真的在拦，不是走过场 |
| 盲解一致率 | 出题答案与盲解答案符号等价的比例 | 证明答案可信 |
| 难度双评一致性 | Cohen's Kappa | 证明难度标注不是随手贴的 |
| 判卷一致性 | 同一份作答重复判卷的分数方差 | 证明判卷可复现 |
| 手写识别准确率 | 抽检样本的公式级准确率 | 主动暴露最弱环节 |
| 用户作答统计 | 各知识点得分率分布（匿名聚合） | 顺带产出一份「真题难度实况」 |

**刷新机制：每 20 秒轮询一次最新数据**（已定）。

实现上要注意两点，否则这个决定会变成成本问题：

1. **服务端做短缓存，不要让每个访客都打一次数据库。** 20 秒轮询 × N 个在线访客 = 每秒 N/20 次请求。正确做法是 Function 侧缓存聚合结果 20 秒，所有访客共享同一份——数据库实际查询频率恒定为每 20 秒 1 次，与访客数无关。
2. **页面不可见时暂停轮询。** 用 `document.visibilityState` 判断，标签页切到后台就停，切回来立即拉一次。否则一个挂着不管的标签页会一直消耗请求。

另外加一个体验细节：**数据更新时给个轻微的视觉提示**（比如数字变化时的淡入），否则用户不知道页面是活的还是卡住了。

**历史趋势图**（已定）：核心指标除了当前值，还要画时间曲线。

| 图表 | 横轴 | 纵轴 | 想说明什么 |
|---|---|---|---|
| 通过率趋势 | 按天 | 一次通过率 | prompt 迭代后质量真的在提升 |
| 题库增长 | 按天 | 真题 / AI 题累计数 | 题库在自我生长 |
| 打回原因演变 | 按天堆叠 | 各类原因占比 | 改进是否命中主要问题 |
| 作答量 | 按天 | 试卷数、题目数 | 有人真的在用 |

**实现要点**：

- **数据源用 `llm_calls.created_at` 和 `attempts.created_at` 按天聚合**，不要另建统计表（数据量小，实时聚合够用，且不会出现统计表与原始数据不一致）
- **趋势图不参与 20 秒轮询**。历史数据变化极慢，按天粒度刷新没意义。前端加载时拉一次，之后每 5 分钟刷新即可——否则每 20 秒重算 30 天的聚合是纯浪费。
- **数据不足时不要画空图**。少于 3 天数据显示「数据积累中，趋势图将在使用 3 天后展示」。空图表比没有图表更让人怀疑。

> 趋势图是这一页最有说服力的部分。静态数字只能证明「现在还不错」，曲线能证明「系统在变好」——后者才是评委真正想看的工程能力。

**三条必须遵守的边界**：

1. **只展示聚合值，不展示任何个体数据。** 不做「某某同学错了这题」，那是隐私问题。
2. **样本量不足的指标要标注。** 「通过率 100%」在只有 3 次调用时毫无意义，必须显示 `n=` 并标注「样本不足」。
3. **指标定义要写在页面上。** 比如「一次通过率 = 首次审核即通过的题目数 ÷ 首次生成总数」。不写定义的数字容易被质疑造假。

**一个诚实的加分项**：如果某些指标不好看（比如手写识别准确率只有 70%），**照样展示**，旁边写「当前已知短板与改进方向」。这比藏起来强——评委看的是你的工程判断力，不是完美数字。

| D4–D5 | 三层检索（改写→别名→闭包展开）+ 组卷引擎（三种题源 + 混合配比 + 整卷模考/专项突破）+ 试卷渲染 | 能听懂人话出卷 | 后端 DB + 函数 |
| D6–D7 | 生成 + reviewer 流水线 + 判卷（客观题） | 能出原创题、能判客观题 | 评测数据中心数据表 |
| D8 | 判卷（解答题 rubric）+ 拍照识别接入 + 整卷诊断 | 完整判卷闭环 | — |
| D9 | 错题本 + 变式 + 复习调度 | 闭环打通 | Agent 工具层 |
| D10 | Agent 对话层 + 人格 + 限流 | 对话可用 | — |
| D11 | 全链路联调、边界处理、部署、截图、论坛帖 | 公网可访问 | 演示视频 |
| D12 | 缓冲 + 提交 | — | — |

**范围冻结（重要）**：只做数学二、只做 2005–2026、只做三种题型、单用户无登录。英语/政治只留接口不实现。任何一天落后，砍的优先级是：变式生成 → 人格 → 对话层（表单入口是底线）。

> 拍照识别**不在砍单名单里**——它是解答题的唯一可行输入方式，砍掉等于解答题没法做。

## 13. 风险与降级

| 风险 | 触发 | 降级方案 |
|---|---|---|
| 生成题质量不稳 | 一次通过率 < 50% | 提高真题比例，生成题默认关闭、显式开启并标注「AI 原创·已校验」 |
| 解答题判卷不公 | 用户/评委质疑 | 每题展示 rubric 与命中项，提供「我不同意」申诉入口 |
| 手写识别失败 | 演示现场 | 允许切到文本输入兜底；演示前准备识别效果好的样例作答，不现场手写 |
| Sites 数据库 DDL 限制 | 迁移被拒 | 先在本地 SQLite 验证 schema，再映射到允许的语句集 |
| LLM 被刷 / 超预算 | 公网暴露 | 函数级限流 + 每日配额 + 结果缓存（同参数组卷直接复用） |
| 版权质疑 | 被问数据来源 | §4.3 的做法：不提供原卷下载、标注来源、如实说明流程 |
| 工期不够 | 任意一天 | 按 §12 的砍单顺序执行 |

## 14. 已定事项与待定事项

### 已定（这几轮讨论的结论）

| 决策 | 结论 | 理由 |
|---|---|---|
| 真题的形态 | **跨年份抽题重排**，不做原卷还原 | 用户要练真题的「题」，历史整卷市场上到处能买到 |
| 题源结构 | **真题 / AI 仿真 / 混合**三选一，共用一个组卷器 | 避免三套流程；混合模式真题优先、AI 补缺口 |
| 组卷模式 | 整卷模考（梯度铺开）/ 专项突破（单档扁平） | 档位不产生梯度，排序才产生梯度 |
| 分值 | 照实显示，不重分配 | 用户自己选题型数量，本就知道；省掉解释成本 |
| 成绩口径 | 一律给**得分率**；混合卷按真题/AI 分开报 | 卷面总分不同；分开报能暴露 AI 题难度标偏 |
| 大题拆分 | **一个题号 = 一道题**，小问进 `sub_items` | 按题号切分，不判断是否共享题干，避免拆出无解题目 |
| 题目-知识点 | 多对多，**无主次**，组卷按任意关联筛选 | 有 primary 会导致漏题 |
| 难度 | **易/中/难三档** + 得分率区间标注 | 三分类标注一致性远高于连续打分 |
| 难度校准 | 第三方教研机构的难度数据做锚点 | 官方不逐题公开；但必须记录来源 |
| 试卷输出 | 前端 KaTeX 渲染，**不做 PDF/Word** | 交互是核心价值；Sites 上生成 PDF 不可行 |
| 试卷存储 | 题目 ID 列表 + 结构模板 | 存文档会锁死重排、回看、导出等能力 |
| 部署平台 | Qoder Sites（含后端） | 赛事要求；能力见 §10.1 |
| **题库范围** | **2005–2026（约 501 题）** | 结构接近现行；旧卷差异大、线代只到 1997、解析成本高 |
| **作答输入** | **拍照手写 + 多模态识别**，识别结果可修正 | 键盘敲数学公式对用户不现实，解答题过程必须手写 |
| **登录鉴权** | **不做登录**，匿名 `device_id` + 本地存储 + 导出备份 | 公网 demo，登录会劝退评委；代价见 §9 |
| **模型分工** | 生成 / 判卷**分开** | 降低自一致性错误；盲解与出题同源同 prompt 会犯同样的错 |
| **评测数据中心** | **公开页面，20 秒轮询刷新** | 主动公开通过率与打回原因，把最大质疑变成专业度 |
| **AI 题归属** | **与真题同池**，前端强制标注来源 | 一次生成可复用多次；但必须让用户分清真伪 |
| **AI 题纠错** | **举报即隐藏，手动复核裁决**，不做自动下架 | 自动下架会被恶意举报滥用；误判成本高于晚修 |
| **导出** | **不做 LaTeX 源码导出**，用打印代替 | 用户拿到编译不过的 .tex 体验更差；打印已够 |
| **混合配比** | **真题 : AI = 1 : 1**（目标是目标，不足按实际） | 保真度与新鲜度各半；两部分样本接近，得分率对比才可靠 |
| **题目上限** | **单卷最多 30 题**（所有模式） | 超过 30 题完成率会崩 |
| **知识点树** | **2 门 + 11 章 + 124 考点 = 137 节点** | 章名只能粗筛，打标和诊断需要三级节点 |
| **检索入口** | **别名层 + 闭包表展开 + LLM 查询改写**，不用向量做主路径 | 实测 13 个常用词精确命中叶子数为 0；用户说粗粒度词，靠树展开 |
| **多考点** | 一句话可含多个考点，全部抽出 | 用户不会一次只说一个知识点 |
| **降级顺序** | **先放宽知识范围（往父节点升），再放宽难度** | 用户对范围放宽的接受度远高于难度错配 |
| **评测趋势图** | **做**，按天聚合，5 分钟刷新 | 曲线证明「系统在变好」，比静态数字有说服力 |

## 附录 A：抽取会踩的具体坑（实测）

| 现象 | 例子 | 处理 |
|---|---|---|
| 分式被拉平成两行 | `a = 1` / `3` 实际是 `a = 1/3` | 按 x 区间重叠 + y 相邻判定分子分母 |
| 矩阵括号变成私有区字符 | `\uf8ec \uf8f7` 等 126 个 PUA 字符 | 用 bbox 定位括号，重建 `\begin{pmatrix}` |
| 积分上下限错位 | `\int` 的上下限被排到另一行 | 按 x 相对位置归位 |
| 旧卷编号体系不同 | 1987 年选择是「九(1)–九(4)」，填空是「一(1)–一(5)」 | 按 section 标题切分，不按数字顺序 |
| 页眉页脚混入正文 | 「真题试卷 / GitHub 项目仓库 anki-pipeline / 页码」 | 按 y 坐标裁掉页边区域 |
| 图形题 | 约 40 余处「如图」 | 按题目 bbox 裁切为 PNG 存 storage，题干留占位符 |
