## Context

工作区目前只有 40 份数学二 PDF 和一份产品方案，没有代码。产品形态已经讨论并冻结，下一步不是继续加功能，而是把方案变成一套能并行开发、能逐步验收、能按期发布的实施计划。

本开发文档以 [考研助手-参赛方案-v0.1.md](C:\Users\hp\Desktop\kaoyanagent\docs\考研助手-参赛方案-v0.1.md) 为产品依据，不改变其中已定决策。核心是回答四个问题：先做什么、哪些能派给子 agent、哪些必须由主线亲自负责、开发过程中如何防止返工和“演示能跑但线上不能用”。

## 一、开发总原则

### 1. 不直接全面铺开，先打穿一条真实闭环

最小纵切：**选一个知识点 → 组出一张真题卷 → 提交客观题作答 → 判卷 → 错题入本 → 下次复习可查到。**

这条链路必须在本地跑通，再让不同模块并行扩展。一开始就做“501 题解析 + 整套 AI 生成 + 对话 + 拍照 + 报告”会产生大量无法集成的半成品。

### 2. 先冻契约，再允许并行

模块能并行开发的前提，不是目录分好了，而是下面几项已经被主线固定：题目结构、试卷实例、作答结构、状态机、API 路由、模型任务协议、匿名数据边界。

子 agent 只实现具体模块，不得自行修改公共契约、状态枚举或全局路由。契约变更由主线评审后统一修改。

### 3. 本地夹具不能代替平台验证

Qoder Sites 发布预览只渲染静态前端，不执行 Function。数据库、Storage、QCA、VLM、真实身份都必须在正式发布后验证。

因此要在早期做一次**小规模真实后端冒烟**，而不是等到 D11 才第一次部署。发布请求和开启能力仍需用户授权；涉及 QCA 时要先确认创建并使用 Qoder PAT。

### 4. 离线数据管线和线上应用分开

PDF 解析、LaTeX 重建、答案对齐、知识点标注、难度标注全部在本地 Python 中运行，生成可审计的 JSONL 和报告。线上站点不解析 PDF，也不依赖本地文件系统。

原始数据不直接进线上数据库，先经过切分对账、内容抽检、答案对齐和人工复核。

### 5. 匿名不是可信身份，公共池不是任意写入口

用户数据按 `device_id` 分桶，但该值可以被伪造，只能当匿名演示中的数据隔离约定，不宣称安全身份。题库、知识点和公开评测聚合可公开读；AI 生成、判卷、举报和管理导入必须经过服务端限额、校验和归属判断。任何管理操作都不能混入匿名业务接口。

## 三、开工前必须先修正的契约缺口

探索发现，以下问题如果不先修正，会让前端、判卷和错题模块互相返工。

### 1. 拆清原卷与生成试卷实例

现有 `papers` 是原卷来源表，不能同时承载用户组出来的卷。新增：

```sql
CREATE TABLE app.paper_instances (
  id uuid PRIMARY KEY,
  device_id text NOT NULL,
  mode text NOT NULL,              -- exam / drill
  source_mode text NOT NULL,       -- real / ai / mixed
  config_json jsonb NOT NULL,
  items_json jsonb NOT NULL,       -- 固定题序、题目版本、来源与实际配比
  total_score_x2 integer NOT NULL,
  status text NOT NULL,
  created_at timestamptz NOT NULL,
  submitted_at timestamptz
);
```

`attempts` 关联 `paper_instance_id`，而不是原卷 `papers.id`。`items_json` 是试卷快照，后续题目下架不能改变已经做过的试卷。

### 2. 统一状态机

题目只允许：`draft → reviewed → published → hidden/rejected`。组卷只读 `published`。举报记录使用自己的 `open/resolved/rejected`，被举报 AI 题进入 `pending_review` 且立即从组卷池排除，复核后回到 `published` 或转 `hidden`。不能把举报表状态与题目状态混用。

### 3. 答案与评分细则分开存

`answer_source` 只用 `official` / `ai_verified`。题目增加 `rubric_json`、`rubric_source`、`rubric_version`。`rubric_source` 用 `derived_official` / `ai_verified`。判卷必须记录 rubric 版本，旧作答不能因 rubric 更新而改变历史成绩。

### 4. 错题必须可回看当时作答

`wrong_book` 增加 `attempt_id`，关联不可变作答；判卷报告、识别稿、原始答案和 rubric 证据均从该 attempt 读取。照片是否长期保留采用显式保留策略，避免 Storage 永久堆积。

### 5. 明确组卷优先级

硬约束：题型、题量上限 30、题源标注、试卷快照。软目标：模考 3:5:2 梯度、混合 1:1。专项模式优先满足用户所选难度档，不强行套 3:5:2。

候选不足时：先父节点扩展 → 再相邻难度 → 最后 AI 补足。每次降级都返回 `adjustments[]`，由前端显示实际变化。

### 6. LLM 长任务不能依赖长请求

新增 `generation_jobs`：`id/device_id/kind/status/progress/result_json/error/expires_at`。生成、盲解、审核按步骤推进，每个请求只做有界工作；前端轮询任务状态。SSE 只用来显示进度，不作为完成依据。

### 7. 匿名与聚合数据边界

评测中心不得返回 `device_id`、用户原始作答、题目级用户轨迹、原始 prompt 或密钥。20 秒轮询的短缓存不能假设 Edge Function 进程内缓存可跨实例共享，使用带 `expires_at` 的 DB 聚合快照；趋势图按天聚合且每 5 分钟刷新。

## 四、执行顺序与每日交付门槛

### P0｜11 月 18 日：契约冻结和可行性样例

**主线亲自做**：冻结上述契约；建立 API 错误码；确定题目状态迁移；写一题包含分式、矩阵、共享小问、答案、rubric 的完整 JSON 样例。

## 五、子 agent 使用规则

### 可以直接多派发的任务

1. **数据探索**：只读检查 22 份 PDF、坐标/跨页/题号内小问、答案格式。彼此按年份或问题类型分片。
2. **平台资料探索**：分别核对 Function、数据库、Storage、QCA、发布流程。只读，不创建资源。
3. **独立模块实现**：在契约冻结后，前端、生成、判卷、复习、评测可并行，各自目录不同、测试独立。
4. **独立验证**：501 题数据审计、手写样本、判卷一致性、限流/伪造 `device_id`、发布后公网验收。验证 agent 不能由实现同一模块的 agent 兼任。
5. **文案与交付材料**：论坛帖、演示脚本、截图清单可以并行准备，但不得由助手自行公开发布。

### 必须由主线亲自负责

- 公共 schema、状态机、API 契约与匿名边界。
- 唯一 Function 的路由、模型配额、Secret 管理。
- 组卷器、试卷实例与题目快照。
- 数据合并、跨模块集成、真实部署、发布与最终验收。
- 所有需要改变产品范围、创建 Qoder PAT、启用付费/公开能力的事项，必须先向用户确认。

### 给子 agent 的任务卡必须包含

背景和目标、允许读写的路径、已冻结契约版本、输入输出样例、不可修改文件、验收命令、平台/时间约束、报告格式。不要只写“实现某某模块”；不要派多个 agent 同时修改 `contracts/`、`routes.mjs` 或同一批解析产物。

## 六、开发过程中必须长期守住的检查点

### 数据可信

- 501 题逐年对账；跨页题和题号内小问不得漏。
- 每题保留原卷年份、题号、页码、bbox 与内容 hash，修正可追踪。
- 题目正文用 LaTeX，但 SymPy 仅用于本地数据校验；线上 Function 是 Deno，不能假设可运行 Python。线上客观题比较采用已归一化答案、白名单数学函数和服务端复核，不把未验证的 LaTeX 直接求值。
- AI 题与真题同池但强制标注，分开报得分率；AI 生成题只能由审核通过的服务端任务进入公共池。

### 判卷可信

- 选择题和填空题由服务端取答案判定，客户端不能提交分数。
- 解答题模型输出步骤命中与原文引用，服务端按 rubric 重算并封顶。
- 拍照保留原图、识别稿、用户确认稿；识别不确定必须让用户修正，不能直接判卷。
- 记录模型、prompt hash、rubric 版本，确保相同输入可复核。

### 成本与可用性

- 上传限制类型、大小、页数；不自动重放未知写入。
- 模型调用按 device 和全站分别限额；优先复用已审核公共变式。
- 长任务采用任务表与有界轮询；前端不可见时停止指标轮询。
- 管理导入、举报复核、密钥与公开业务接口彻底隔离。

### 平台与交付

- Function 使用自包含相对导入，入口为 `functions/index.ts`，不打包 `_qoder/`。
- 受限 DDL：表放 `app` schema；标签/小问/ rubric 用 jsonb；分值用 integer 半分制。
- 前端设计变量必须实际被样式消费；站点通过 `open_design_workbench` 登记真实页面和能力。
- 发布预览不是后端验证；正式发布后必须完成一次浏览器 → Function → DB/Storage/模型全链路。
- 临时验证页面在结束后关闭；本地夹具、样例图片和 dev 服务不进入发布包。
- 论坛帖和社交媒体内容先准备，用户确认后才发布。

## 七、最终验收清单

1. 用自然语言和表单各组一张卷，覆盖真题、AI、混合和两种组卷模式，最多 30 题且展示降级原因。
2. 完整试卷有题序、分值、来源和题目版本快照；刷新后恢复。
3. 选择/填空正确判定，解答题 rubric 逐步给分且可查看原文证据。
4. 拍照识别失败、用户修正、文本兜底都可完成。
5. 错题入本后能看当时作答；相似推荐可解释；变式已审核；到期复习正常。
6. 公共池只读 published；举报立即隐藏，复核能恢复或下架。
7. 评测页只显示聚合值与样本量；趋势按天；不泄露用户作答或密钥。
8. 匿名伪造、重复提交、超额生成、上传过大、模型超时均有明确处理。
9. 公网正式站点完成端到端验证，不是只看发布预览。
10. 论坛帖、Qoder 开发过程截图、3 分钟演示脚本和可恢复演示数据齐备。
